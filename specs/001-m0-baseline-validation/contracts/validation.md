# M0 验证与证据契约

这是正式实现阶段应满足的验证协议。规划期 `spikes/` 的输出只证明各自测试过的条件，不自动充当本协议的完整验收。

## 1. 身份与不可变输入

每次运行绑定 `sample_id`、样本清单 SHA-256、数据 SHA-256、配置 SHA-256、环境版本清单及代码修订身份。工作区未提交时另外保存源码清单和文件哈希，不能只写 Git HEAD。

参考运行不覆盖冻结输入或前一次结果；不同配置生成独立运行目录。恢复已有输入时必须核对内容哈希，远端不可用不妨碍已冻结数据的离线计算。

样本与参考输出均禁止使用非标准 JSON 的 NaN/Infinity。结果摘要不能代替数据文件与配置。

## 2. 输入验证

不同层次分开处理：

| 层次 | 必须检查 |
| --- | --- |
| 来源与样本 | 起报身份、目标有效时刻、声明的完整成员集合、实际空间点集合、单位与转换、数据来源和使用条件 |
| 计算任务 | 非空成员列表、非空唯一成员 ID、非空特征、任务内相同长度、有限数值、所有嵌套层非 NULL |
| 参考算法 | 至少支持两个非退化投影维度、三个可区分成员向量及三簇设置 |

数值相同但身份不同的成员允许进入往返接口。参考算法检查可区分向量总数，不能静默删掉重复向量。常量特征保留，由参考标准化规则处理。

可排序的乱序输入按样本契约规范化；重复身份、重复点键和不同成员缺点不能通过排序“修复”。往返函数本身不重排输入。

## 3. 数值对照

- 固定 `float64` 参考计算、标准化、二维投影、三簇配置以及随机初始化设置。
- 每次验收至少启动三个独立进程，不能以同一进程连续调用替代。
- 按 spec 的 `atol=1e-8`、`rtol=1e-6` 检查可比数值。
- 以共簇关系或成员集合比较分区，不能直接比较任意簇编号。
- 相同子空间的投影允许符号翻转；验证投影几何可用投影矩阵或成员间距离。只有同一拟合与对齐规则下的坐标才能逐项比较。
- 固定环境复跑先按每个分量内最大绝对载荷为正规范化符号；相应同步变换投影坐标与簇中心。若退化奇异值导致基向量旋转，检查保留子空间投影矩阵及成员间距离，并要求成员分区仍一致；在保留/舍弃维度边界退化、不能确定相同子空间时报告失败，不自动放行。
- 标准化矩阵、均值、尺度、解释方差、惯性分别按各自意义比较；不能仅用投影几何替代所有中间结果检查。簇中心须先按成员分区对应并采用同一坐标对齐规则。
- 比较器必须通过反例：标签重命名和符号翻转应通过，移动一个成员到另一个簇或修改超过容差的数值应失败。
- 有效秩的数值判定阈值与配置一起保存；不得只凭特征列数判断秩。
- 此处证明参考基线重复性，不声称 M1 的不同算法、随机数生成器和初始化已经数值等价。

## 4. 往返、批量与错误恢复

正向测试覆盖单任务、多任务、不同任务合法的不同形状、字符串 ID、单成员单特征，以及超过宿主一次处理批量的成员列表和任务行集合。

批量边界测试使用随行变化的成员 ID 或特征并核对每行预期值，避免常量折叠把大量相同输入优化成一次求值。性能测量仍使用固定矩阵，但在构造任务身份时让函数输入包含可核对的逐任务差异；记录实际执行方案及优化影响，不把重复常量的广播耗时称为多次计算耗时。

并发至少使用两个独立连接同时执行同一份任务，各自比较完整输出；这不等于已证明单个连接支持多线程并发访问。

每种异常测试使用同一连接依次执行：

1. 一个合法任务成功。
2. 一个非法任务明确报错。
3. 再执行合法任务成功。

非法类别包括：顶层 NULL、空成员列表、NULL 成员、NULL/空成员 ID、重复 ID、NULL/空特征列表、NULL 元素、NaN、正负无穷、任务内特征长度不一致。类型绑定错误也算拒绝，但应区别于函数内数据验证错误。

混合有效/非法任务的调用整体失败，不提交部分通过记录。数据库允许流式传输时，验证者必须完整消费查询后才能标记成功，不应将先收到的行视为完整成功。

## 5. 资源测量

使用同一份合法矩阵分别构造 1、10、100 个任务；每个规模记录任务数、成员数、特征数、输入/输出字节数、宿主线程设置、墙钟时间和进程峰值 RSS。

冷启动与已加载调用分开标记；峰值 RSS 包含宿主及测量程序时须明确，不把它写成 core 的独占内存。无法分离的转换和计算成本记录为未分离，不伪造分项计时。

测量不设吞吐量通过阈值；正确性、完成执行和如实报告是门禁。并发结果须与串行一致。

## 6. 参考工具隔离

正式验收需提供无参考 Python、CDO、wgrib/wgrib2 工具的最小运行环境，执行扩展加载、合法输入与错误恢复。仅设置空 PATH 或检查链接依赖不足以证明环境隔离。

构建打包辅助脚本可以使用开发工具；计算 crate 的依赖图和运行路径不得引入参考工具。记录动态链接检查作为辅助证据，不代替实际运行。

## 7. 证据状态与总判定

每项 FR 对应一个或多个记录：

```text
requirement_id, status(pass|fail|not_run), scope,
input_hashes, configuration_hash, environment,
steps, expected, actual, artifacts, limitations
```

状态转换为 `not_run -> pass|fail`；复跑保存新记录，不擦除失败历史。受阻用例使用 `not_run` 并写明阻碍，不把“设计了测试”标为通过。

总体通过仅在 FR-001 至 FR-014 全部有满足要求的证据时产生。目录存在、研究完成、编译成功、spike 通过或质量清单勾选都不能单独推出 M0 通过。

对应规格：FR-001 至 FR-014、SC-001 至 SC-006。
