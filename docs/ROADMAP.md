# ensabc 项目现状与完整技术路线

记录日期：2026-10-20

本文记录项目重启时的上下文与后续路线。阶段按依赖和验收条件推进，不构成工期承诺。后续调整直接更新本文，并在末尾记录关键决策变化。

## 1. 目标与方向

将现有集合预报探索代码逐步发展为可通过 SQL 调用的情景与概率计算库：

1. 可靠、可复现的单批次情景计算。
2. 围绕同一目标有效时间的跨起报情景匹配与追踪。
3. 情景分裂、合并、消失及权重变化分析。
4. 基于历史数据验证概率校准、预报修正预测及下游应用价值。

第一版可发布结果以单批次计算为目标；跨批次追踪是后续重点能力。算法可解释性和预测价值分别验证，不以图表效果代替验证结果。

## 2. 决策状态

### 已选定方向

- Rust core 实现相关计算，保持独立于 DuckDB。
- core 使用原生 Rust 实现或 Rust 包；不通过 Python、CDO、wgrib/wgrib2 子进程执行核心算法。
- CDO、wgrib/wgrib2 等可按需安装在验证环境，用于独立检查与生成参考结果，不进入 core 的构建、运行或部署依赖。
- DuckDB extension 提供 SQL 调用接口与数据转换。
- DuckDB 通过 DuckOMO 获取天气数据。
- 基于现有 ensabc 工作继续推进；保留 Python 教程作为研究与参考资产。
- 采用分阶段路线，先复现与验证，再扩展能力。

### 当前规划基线

以下作为开展工作的默认方案，可在实验后调整，不代表接口已经冻结：

- 在同一仓库新增 `ensabc-core` 和 `ensabc-duckdb`。
- core 无数据库和网络副作用；历史状态由 DuckDB 表保存。
- native Linux 优先；WASM 与其他平台按实际需求单独验证。
- 首个案例沿用区域气温集合，先完成单变量、单有效时刻的空间场聚类。
- 先验证有序列表批量输入，再决定最终 SQL 函数形式。
- 跨批次匹配先采用带拒绝条件的一对一关联。

用户已同意沿上述路线继续规划并记录。M0 已选 Linux ARM64、WeatherBench2 IFS ENS 历史 2 米气温区域场；这是验证样本，不是首发业务场景或最终产品默认配置。

### 尚未确定

下列主要指长期产品决策。M0 的实验版本、二维投影/三簇参考配置和 echo 签名已在 [技术计划](../specs/001-m0-baseline-validation/plan.md) 中固定，不自动成为 M1 之后的产品默认值。

- Rust 数值计算依赖、初始化策略、PCA 维度及最终聚类算法。
- 特征标准化、空间权重、缺失值策略和匹配距离。
- 最终 SQL 函数名称、类型签名和数据交换实现。
- DuckDB、Rust 工具链及扩展依赖的具体版本。
- 历史样本来源、时间跨度、观测来源和评估阈值。
- 分裂与合并规则、多模型权重、校准方法和修正预测模型。

概率产品 notebook 的实际基线：

```text
区域成员场
  -> 展平为成员 × 网格特征
  -> StandardScaler
  -> PCA(n_components=2)
  -> KMeans(n_clusters=3, random_state=0, n_init="auto")
  -> 聚类均值场与成员地图
```

它包含固定历史日期、本地 NetCDF 路径和维度顺序假设。当前未见独立封装的聚类接口、跨批次匹配、概率校准、Rust workspace、DuckDB 扩展或自动化测试体系。不要把教程标题中的“概率产品”视为已完成概率校准。

## 4. 技术分工

```text
DuckOMO / 固定测试样本
          |
          v
DuckDB SQL：筛选、分组、显式排序
          |
          v
ensabc-duckdb：输入校验、类型转换、结果回传
          |
          v
ensabc-core：情景计算与匹配
          |
          v
DuckDB：保存计算结果与历史
          |
          v
Notebook / 下游应用
```

| 部分 | 职责 |
| --- | --- |
| Rust core | 接收数值及显式参数，返回结果；不隐式读取历史状态 |
| DuckDB extension | 处理 SQL 类型、NULL、形状校验与 core 错误映射 |
| DuckDB SQL | 数据选择、分组、普通统计、结果与历史持久化 |
| DuckOMO | 提供天气数据；具体字段与输出结构需联调确认 |
| Python | 参考计算、研究实验、图表、迁移对照 |
| CDO / wgrib / wgrib2 等 | 验证环境的可选工具；独立检查文件或计算参考结果，不作为 core 后端 |

core 应能使用固定数值样本独立测试。DuckOMO 联调与算法迁移可以并行，但首个端到端版本必须验证实际数据接入。

数据来源与核心计算分离。DuckOMO 负责 OM 路径；M0 规划选择 WeatherBench2 历史集合小区域样本，Dynamical 和 Open-Meteo Ensemble API 保留为后续来源候选。不能把“公开 OM 中尚未落实真实集合样本”扩大为“没有可用的开放集合数据”，也不要求 core 为数据格式增加依赖。

建议在实现时逐步形成以下目录，不预先创建空模块：

```text
Cargo.toml
crates/ensabc-core/
crates/ensabc-duckdb/
ensabc/
tutorial/
tests/fixtures/
docs/
```

## 5. 数据与算法契约

### 情景定义与输出

第一版默认：一个模型、区域、变量、目标有效时刻上的成员空间场聚类。之后扩展到时间窗口内的完整轨迹和多变量情景。

建议输出：

- 成员到 `cluster_id` 的归属。
- 簇中心和最接近中心的真实成员。
- `member_fraction`，明确表示成员占比。
- 簇内离散程度、拟合误差等诊断信息。

控制成员是否参与聚类、是否与扰动成员同权，须在样本契约中明确。经过观测验证与校准之前，不把成员占比直接命名为校准概率。

### 跨批次可比性

单批次聚类空间和跨批次匹配空间分别定义：

- 先复现现有标准化与二维 PCA 流程，再评估替代方案。
- 不直接比较两个批次分别拟合得到的 PCA 坐标。
- 匹配使用统一网格、单位、空间权重、目标时间下的物理场或固定特征。
- 如采用共享标准化/PCA，记录拟合时间范围与特征版本。
- PCA 维度、聚类数、距离和门槛由实验决定，不把教程常数直接冻结成产品默认值。

### 时间与标识

围绕同一个 `valid_time` 或 `target_window` 比较不同 `init_time`。不要把不同起报的相同预报时效误当成同一目标时间。

数据契约至少区分：

| 字段 | 含义 |
| --- | --- |
| `model` | 预报模型 |
| `init_time` | 起报时间 |
| `valid_time` / `target_window` | 目标有效时间或窗口 |
| `member_id` | 批次内成员标识 |
| `feature_version` | 网格、变量、变换及权重约定的版本 |
| `cluster_id` | 单次聚类内的编号 |
| `branch_id` | 跨批次追踪的持续身份 |
| `available_at` | 历史实验中数据实际可用的时间 |

多区域、多变量扩展时需显式纳入任务标识，避免不同情景任务相互匹配。保存历史样本时同步记录数据来源、算法配置和版本。

### 匹配语义

- 先做带距离门槛的一对一匹配，返回匹配距离与未匹配项。
- 允许拒绝关联，不强制所有情景都拥有前驱。
- `branch_id` 分配与持久化由显式流程管理。
- 分裂、合并作为后续多对多关系单独建模。
- 图中的权重流动是关联算法的解释，不能直接视为跨起报成员迁移的事实。

### SQL 输入与运行约束

先验证按任务聚合为有序列表的接口。成员 ID 与特征绑定在同一结构中，防止独立列表排序错位。具体类型与函数名在实验后确定。

需要验证空输入、NULL、非有限值、重复成员 ID、维度不一致、无效聚类数、退化输入及错误回传。对多个任务同时执行时的内存占用进行检查，分别测量转换和计算成本。

  仓库**；仓库只提交清单、源 generation 证据和恢复步骤，验证者用

  载荷。若后续需要随仓库分发样本，应切换到许可明确的来源（如 Dynamical

- 验收平台只覆盖 Linux aarch64 + DuckDB CLI 1.5.5。其他宿主版本、x86_64、

- 正式原生聚类移植属于 M1。M0 的扩展只做身份与数值传递的诊断往返，不产生

- 追溯矩阵的断言由本轮实现编写，覆盖面受编写者对 FR 措辞的理解限制；它能
  证明“报告没有超出证据所支持的范围”，但不能证明“每条 FR 已经被穷尽所有
  可能解释地验证”。
- 独立验证者复现已在本轮实测（见 quickstart 第 8 节），但复现使用的是同一台
  机器、同一网络与同一组已缓存的 Python 环境；换一台机器的完整复现未执行。

这两条实验线可并行。此阶段无需全面重构旧下载器或一次性恢复所有教程。

- [ ] 与原始集合、简单统计或持久性等适当基线比较。
- [ ] 在留出数据上报告稳定性、失效案例和适用范围。

完成标志：相对明确基线有可重复的证据。概率目标可采用 Brier、CRPS 等适用指标；具体指标须随目标定义。交易表现只在另行定义业务执行、成本和约束后评估。

若没有稳定收益，记录负面结果并调整假设，不以更复杂的模型替代验证。

## 7. 验证原则

| 层次 | 重点 |
| --- | --- |
| 算法迁移 | 固定输入与初始化，对照中心、目标函数和成员划分；消除簇编号置换影响 |
| 聚类质量 | 随机初始化、轻微扰动、退化输入和不同维度设置 |
| 匹配逻辑 | 编号打乱、距离过大、无匹配、情景数量变化 |
| 实际案例 | 同一目标时间的连续起报回放 |
| SQL 集成 | 数据形状、NULL、错误传播、分组隔离、内存与转换成本 |
| 预测实验 | 时间留出，变换和门槛只使用当时可获得的数据 |

区分“实现正确”“情景可解释”和“预测有收益”三个层次，分别提供证据。

## 8. 后续扩展顺序

在 M1、M2 稳定后，默认按以下顺序考虑；部分研究可以与 M3、M4 并行：

1. 区域时序情景：从单时刻扩展到完整时间窗口。
2. 多变量及情景条件下的影响分布：温度、风光出力、负荷等。
3. 多模型融合与概率校准：明确相关性、权重与训练样本。
4. 预报修正预测：利用历史情景演化特征。
5. 更多部署平台、WASM、发布渠道与下游集成。

WASM 如为首发要求，应提前到 M0 验证。native 扩展与浏览器端分别测试，不将 core 能编译为 WASM 等同于 DuckDB-WASM 扩展可直接加载。

## 9. 暂不投入与风险

首阶段暂不建设常驻情景服务、通用调度平台、完整交易系统、复杂自定义查询执行器或大规模多模型融合。普通统计优先由 SQL 完成，不为每项统计新增 Rust 函数。

| 风险 | 处理方式 |
| --- | --- |
| 历史教程环境和数据不再可用 | 从固定小样本恢复基线；实时路径另行验证 |
| DuckDB 扩展版本与嵌套类型支持 | M0 实际构建和加载，锁定版本 |
| 数据转换成本或内存过高 | 分别测量转换与算法；再决定是否优化接口 |
| 不同批次特征不可比较 | 固定目标时间、网格、单位与特征版本 |
| 匹配制造虚假的连续性 | 允许拒绝，保留距离和未匹配结果 |
| 缺少连续历史起报和观测 | 及早确认存档与可用时间记录 |
| 情景有解释性但无预测收益 | 分阶段验证，允许记录负面结果 |
